The strongest new mechanism is **coherence debt**. A repository edit depends on
facts elsewhere: a test oracle, an import name, a configuration type, a migration
rule, or a runtime invariant. The study calls the facts covered by neither
current context nor reliable model prior coherence debt. In its controlled
tasks, unavailable facts produced confidently wrong work rather than a clean
refusal. Supplying the required fact restored work even when the fact was far
from the edit, while spending more tokens did not recover a withheld fact.

Two qualifications matter. First, opening files is not proof that the needed
fact was understood or still current. The model may also know a fact without a
read, so read telemetry can both miss real coverage and report false gaps.
Second, more instructions are not automatically safer. When a written standard
conflicted with code, agents followed the stale standard even when that produced
worse code. The useful target is not a larger prompt; it is a small set of
authoritative, current, mutually consistent facts at the moment of the edit,
followed by an output oracle.

The multi-agent paper adds a related but distinct signal. Shared files reduced
repeated one-to-one communication for work whose specification was distributed,
but added overhead when a pipeline already coordinated through files. Merely
naming one agent as coordinator did not create a communication hub or reliable
success gain. Its practical lesson is conditional: coordination topology should
follow the dependency shape of the work, and the interaction structure must
actually implement a role that a prompt names.

## Learning Article

### Coherence debt: the missing facts behind a confident wrong edit

A useful mental model is to treat every meaningful repository edit as having a
small **working set of facts**. If an agent changes a configuration loader, the
edit may depend on the configuration schema, the current default, a deployment
override, the tests that define expected behavior, and the runtime version. The
facts do not need to be in one file or next to the edited line. They do need to
be available, current, authoritative, and mutually consistent when the edit is
made.

You can model it as:

`edit-coupled facts - current trusted facts available at edit time = coherence debt`

Coherence debt is dangerous because it rarely looks like an empty context. The
agent still has a task, source files, general training knowledge, and an urge to
make progress. When one required fact is missing, it may guess a value, invent a
file, use an API it remembers from another version, or follow a stale convention.
The result can be internally polished and locally plausible while being
incoherent with the rest of the repository.

This matters for software delivery because repository correctness is coupled.
A renamed symbol must agree with every caller; a migration must agree with both
the deployed version and rollback path; a test must agree with product behavior;
and a configuration change must agree with its parser, environment, and runtime.
More tokens or more files do not fix a missing authoritative fact. A long prompt
can make the problem worse when it contains stale or conflicting guidance.

Before today, this harness already required agents to load the repository in a
defined order, prefer current project patterns, preserve user changes, verify
behavior rather than file existence, and report unavailable evidence as not
verified. Those practices lower coherence debt. The harness did not, and still
does not, require a universal manifest of every fact coupled to every edit. Today
recorded the empirical signal but deliberately did not add such a rule. There
was no reproduced harness miss, the evidence is concentrated on cross-file
migrations, and a generic harness cannot know whether code, docs, a schema, a
test, or an operator decision is authoritative in each project.

Consider another project upgrading a payment library. The adapter now expects a
boolean retry flag, an old internal guide says the value is the string
`"enabled"`, the lockfile pins a version newer than the guide, and integration
tests exercise the real boolean contract. A poor workflow asks the agent to
"update retries" and counts how many relevant files it read. A coherence-aware
workflow first identifies the coupled facts: pinned library version, official
API for that version, local adapter signature, configuration schema, deployment
override, and behavioral test. It resolves the guide conflict, records which
source wins and why, makes the smallest edit, and validates the resulting
behavior. If another worker owns the deployment file, the handoff includes the
resolved boolean contract and its version rather than only "update the config."

The idea has limits. Teams cannot enumerate every dependency in advance, and a
fact can become stale after it is captured. A file read is only a weak proxy for
understanding; model memory can be correct without a read and confidently wrong
without one. Automatically generated dependency graphs miss prose rules,
runtime state, dynamic dispatch, and human decisions. The paper's evidence is
mostly migration-shaped, so single-file or green-field work may gain little from
extra ceremony. Finally, coherence is necessary but not sufficient: an agent can
have every relevant fact and still reason badly, write weak tests, or discard a
correct change. The practical use is selective—make the fact set explicit for
high-coupling work, keep it current, and judge the output with an independent
behavioral oracle.

## Cross-Project Feedback

- For multi-file migrations, dependency upgrades, configuration changes, and
  delegated edits, identify the small set of facts that must agree at the next
  edit. Record their source and version when staleness would be costly.
- Resolve conflicts among docs, code, schemas, tests, and runtime state before
  editing. Do not make the agent guess which source has authority.
- Invalidate or refresh captured facts after a relevant write, dependency
  update, handoff, or long interruption. Transfer the resolved fact, not only a
  pointer or a task label, across worker boundaries.
- Verify the produced behavior against project-owned tests or state oracles.
  File-read counts and large prompts are diagnostic clues, not proof of
  coherence.
- For agent teams, try shared artifacts only when repeated one-to-one messaging
  dominates; do not mandate another channel when the workflow already passes
  state through files, and do not assume a coordinator label creates routing.

## Knowledge Check

1. What is coherence debt in the working-set model?
2. Why can adding more context or instructions make an agent less reliable?
3. A dependency guide says a retry flag is the string `"enabled"`, while the
   pinned library, local schema, and integration test use a boolean. What should
   the workflow establish before the agent edits the configuration?
4. Why is a log showing that the agent opened every relevant file not proof that
   the edit-coupled facts were available and correct at edit time?
5. Why did today's evidence support a deferred cross-project recommendation but
   not a new generic harness rule?

## Answer Key

1. It is the set of facts required for an edit that are covered by neither the
   agent's current trusted context nor reliable prior knowledge, including facts
   that are present but stale, conflicting, or stranded at a handoff.
2. Extra context helps only when it contains relevant, current, consistent facts.
   Irrelevant material consumes attention, and stale authoritative-looking
   instructions can override correct code or runtime evidence.
3. Establish the authoritative contract for the pinned version, resolve and
   record why the guide is stale, keep the boolean schema and deployment
   expectations available, then validate the edited behavior with the
   integration test or an equivalent oracle.
4. Opening a file does not prove the needed fact was extracted, retained, or
   still current. The model may also supply a fact from prior knowledge without
   reading it, so read telemetry is an incomplete and sometimes misleading
   proxy.
5. The study provides primary controlled evidence and a public artifact, but its
   scope is mainly migration-shaped, no local miss was reproduced, and each
   project must define the authoritative facts, invalidation points, and output
   oracle before the behavior can be tested safely.
