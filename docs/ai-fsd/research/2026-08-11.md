## Learning Article

### The execution envelope is part of correctness

A useful mental model for an agent run is:

`outcome = task + repository + harness + execution envelope`

The execution envelope includes the model and client versions, runtime, identity
or subscription context, available tools, permission policy, and runner. The
code can be identical while one of these inputs changes. When that happens, a
failed command or different plan may be an environment regression, not a code
or prompt regression.

This matters because software-delivery debugging starts by locating the failing
layer. If a team records only the git revision, it may rewrite prompts or tests
when the actual change was a runner policy, client release, expired credential,
or provider update. A small provenance record does not solve the failure, but it
turns an invisible variable into a comparison boundary.

Before 2026-08-06, this harness recorded the repository baseline but not the
agent/model/client/runtime context. The bounded experiment added one required
`Execution provenance` field and a deterministic presence check. Today's
seventh record closes that trial. The field is now applied as a canonical
default because it stayed cheap and made the boundary between documented and
executed behavior explicit. Nothing new was added to the schema today, and the
Claude, Daybreak, and Xcode signals were deliberately not turned into generic rules.

For a concrete example in another project, imagine a CI coding agent whose
shell commands all fail after a runner-policy change, while the same task works
locally. Compare the two runs with the repository revision and task held fixed.
Record the client version, runner image, policy profile, identity mode, and the
first harmless command result. If only the hosted runner with the restrictive
profile fails, the team can investigate that boundary before changing the
agent's instructions. Once fixed, rerun the same small command and the real task
to prove both environment recovery and delivery behavior.

Provenance is not causality or full reproducibility. A stable model label can
hide provider changes, metadata can be wrong, and two equal envelopes can still
produce nondeterministic outcomes. Recording every prompt, tool argument, or
output can also leak sensitive data and create an unusable log. Keep the record
minimal, use digests or references when richer traceability is needed, mark
unknowns explicitly, and rely on behavioral tests for correctness. The common
misuse is to collect versions without ever comparing a failure across them.

## Knowledge Check

1. What belongs in the execution envelope in addition to the task, repository,
   and harness?
2. Why can recording the executed client version prevent an invalid conclusion
   about a feature documented only for a newer release?
3. A CI agent's shell fails under one hosted runner policy but succeeds locally
   on the same commit. What should the team hold constant, what should it
   compare, and what should it test before editing the prompt?
4. What are two limitations or common misuses of execution provenance?

## Answer Key

1. Relevant model and client versions, runtime, runner, identity or subscription
   context, tools, permissions, and explicit unknowns that can explain behavior.
2. It shows that the documented newer client was not the client executed here,
   so its behavior remains unverified rather than being attributed to this run.
3. Hold the task, repository revision, and intended behavior constant; compare
   client, runner, policy, identity, tools, and runtime; then run a harmless
   boundary probe and the real behavioral check in both environments.
4. Provenance records correlation, not causality; stable labels can hide drift;
   metadata can be stale; excessive tracing can leak sensitive data; and records
   add no value if nobody uses them to compare failures.
