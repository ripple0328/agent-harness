LegacyWorld's strongest contribution is not the word *atomicity* by itself. It
measures two independent facts after every run: what the agent reported and what
an external validator observed in persistent state. Combining them yields valid
success, invalid success, valid failure, and invalid failure. That prevents a
conservative agent that rarely completes work from looking useful merely because
it avoids damage, and prevents a productive-looking agent from hiding durable
side effects behind a success or timeout status.

The study is unusually relevant to tool-using agents because its contracts name
an initial state, goal state, allowed changes, forbidden side effects, return
schema, and task-specific validators. However, it is a controlled pre-deployment
study with one included trajectory per model-task-prompt cell. Its atomicity is
only as complete as the monitored observables, and its Windows GUI and legacy
workflow setting does not establish a universal software-delivery gate.

## Learning Article

### Failure has a state, not just a status

A useful mental model for an agent action is two parallel timelines:

`reported outcome: started -> succeeded / failed / timed out`

`observed state: initial state -> actions -> independently validated final state`

The first timeline describes what the worker says happened. The second describes
what the system now contains. For a state-changing workflow, those facts are not
equivalent. A task can report success while writing the wrong record, or report
failure after creating half of the intended artifacts. It can also fail safely,
leaving the monitored state unchanged and ready for a clean retry.

Crossing reported status with state validity gives four outcomes:

- **valid success:** the task reports completion and the intended state exists;
- **invalid success:** it reports completion, but the state is wrong or includes
  forbidden changes;
- **valid failure:** it does not complete, but leaves an acceptable state;
- **invalid failure:** it does not complete and leaves persistent partial or
  unintended effects.

This matters because a single success rate mixes automation value with state
safety. A cautious agent may achieve excellent safe-failure behavior while doing
almost no useful work. Another may complete many tasks while occasionally
leaving corrupted state. Teams need both measures: useful completion tells them
whether automation pays off, while the final-state distribution tells them what
recovery and supervision it needs.

Before today, this harness already preferred behavioral checks over existence,
required data state after commands, called out partial failure and idempotency,
and recommended rollback plus fault injection for high-risk behavior. Today did
not add a universal atomicity rule. The new paper provides strong evidence, but
the generic harness cannot know which files, rows, tags, packages, credentials,
or remote actions a project permits. No local partial-state failure was
reproduced, so adding ceremony without an executable project-owned oracle would
not meet the promotion threshold. The signal is recorded as deferred.

Consider another project's release agent. It updates a version, creates a Git
tag, publishes a package, uploads a signed artifact, and writes release notes.
A good task contract starts from a known commit and absent release, names the
goal state, and lists allowed and forbidden changes. Its validator checks the
package digest, signature, tag target, release metadata, and absence of extra
tags or packages. If publishing succeeds but the tag points at the wrong commit,
that is invalid success. If the registry times out before any durable change,
that is valid failure. If a package is public but the agent times out before
attaching the signature, that is invalid failure and needs reconciliation rather
than a blind retry. The useful adoption is project-local: run the workflow in a
staging registry, inject timeouts around each state-changing boundary, and
classify final state independently of the agent's message.

There are limits. This operational use of *atomicity* is not proof of an ACID
transaction. External services may be eventually consistent, irreversible, or
only partly observable. A validator can miss an unmonitored side effect, and a
rollback can fail. Safe failure can also be gamed by an agent that refuses most
work, so it must never replace useful-completion measurement. Finally, the
allowed and forbidden state contract is a product, data, security, and
operations decision; a generic agent should not invent it.

## Cross-Project Feedback

- Projects that let agents mutate durable state should define the initial state,
  goal state, allowed changes, forbidden side effects, return schema, and
  independent final-state validators before widening automation.
- Report useful completion separately from valid failure, invalid success, and
  invalid failure. Do not count refusal or timeout as safety without checking
  the resulting state.
- Use staging systems, disposable fixtures, or reversible test accounts to
  inject failure before and after each durable boundary. Specify reconciliation
  and idempotent retry when true rollback is impossible.
- Use controlled semantic mutations to evaluate model-based reviewers only when
  the project can define defect families that should reliably make an artifact
  worse; retain safe variants so the judge is not rewarded for rejecting
  everything.
- No adopting project was changed. No feedback event was created because no
  local or repeated generic harness miss was observed.

## Knowledge Check

1. What two independent facts must be measured to distinguish useful completion
   from state safety?
2. Why can an agent with high operational atomicity still be a poor automation
   choice?
3. A release agent publishes a package, then times out before attaching its
   signature and reports failure. Which outcome class is this, and what should
   the workflow do before retrying?
4. Why did today's evidence justify a deferred project-local recommendation but
   not a new generic harness rule?

## Answer Key

1. Measure the agent-reported terminal outcome and independently validate the
   persistent final state against the intended and forbidden changes.
2. It may fail conservatively almost every time. Valid failures preserve state
   but provide little useful completion, so atomicity and success must be
   reported separately.
3. It is an invalid failure because a durable partial result exists. Reconcile
   the registry state first, then complete, compensate, or perform an idempotent
   retry according to the project-owned recovery contract rather than retrying
   blindly.
4. The paper supplies primary evidence for the mechanism, but the harness cannot
   generically define a project's monitored state, side-effect boundary,
   consistency window, or recovery policy; no local miss or executable generic
   fixture was available for behavioral verification.
