The strongest signal is **transfer, not benchmark improvement**. HarnessDev
treats a harness as a frozen runnable artifact and evaluates both initial
creation and later evolution. Generated harnesses lag mature human references
on code, search, and research, while evolution gains are unstable. Of 64
reported executor-model switches, only two were clear improvements beyond the
paper's noise threshold; regressions and benchmark tradeoffs were substantially
more common. Feedback-task and held-out-task movements agreed in direction only
53.1% of the time, and only two of nine declared evolved versions were best on
the held-out evaluation.

That result does not mean an improvement that fails to transfer is useless. It
means the claim must be scoped. A harness edit can improve one task distribution
with one executor while becoming slower, noisier, or worse elsewhere. The
evaluation unit is therefore not merely “the prompt” or “the harness.” It is the
harness, executor, task distribution, and cost budget together.

The specification and release signals sharpen the boundary. Agent Plugins 1.0
can make a skill-plus-MCP package portable, but the standard deliberately does
not make runtime behavior or trust portable. Codex, Claude Code, and GitHub all
changed approval, policy, persistence, or content-exclusion surfaces during the
gap. Those are strong reasons to test host behavior, not reasons to silently
turn a vendor default into a cross-project rule.

## Learning Article

### A harness is not portable until its improvement transfers

A useful mental model is:

`observed delivery outcome = harness x executor x task distribution x budget`

The harness includes instructions, tools, memory, orchestration, and checks. The
executor includes the model, client, runtime, permission system, and versions.
The task distribution includes repository shape, language, risk, and the kinds
of changes being attempted. The budget includes tokens, time, tool calls, and
human review. Change any one of those and an apparent harness improvement may
change direction.

This reframes harness evolution as ordinary software evaluation. First freeze a
baseline harness and a candidate. Run both on the cases that motivated the
change, but also on held-out cases that were not used to write it. Preserve the
same executor and budget for the primary comparison. If portability matters,
repeat a small discriminating subset with a second supported executor. Measure
task correctness and retained invariants before measuring speed or token
savings. Report the supported scope rather than averaging a regression away.

Before today, this repository already required a real signal, an explicit
target layer, positive and counterexample controls for rule changes, unrelated
behavior checks, a rollback, and execution provenance. Those controls make
overfitting harder. They do not prove cross-executor portability, and today's
run did not pretend they do. No universal matrix was added because a generic
harness cannot invent representative project tasks, authoritative oracles, or
an acceptable cost budget.

Consider a payment service whose incident-response skill is changed to retry
API calls after HTTP 429 responses. The edit is motivated by one production-like
fixture where the old skill gives up too early. A weak evaluation reruns only
that fixture until the candidate succeeds. A transfer-aware evaluation freezes
the old and new skills, then checks both against the motivating fixture, held-out
rate-limit patterns, non-rate-limit failures, idempotency-sensitive operations,
and a normal successful call. It records correctness, forbidden duplicate
writes, latency, and tokens. The current production executor is the primary
comparison; a second supported executor is useful only if the team actually
claims portability. A candidate that helps one executor but duplicates a charge
with another is not a universal improvement. It may still be a project-local,
executor-pinned improvement with an explicit boundary.

There are important limits. Multi-executor evaluation is expensive, and one run
per cell can confuse noise with causality. Models and clients drift after the
test. Held-out tasks can still resemble the authoring set. A narrow fixture can
reward ceremony rather than real delivery. Security, approval authority, data
retention, and organizational policy cannot be settled by benchmark averages.
The practical rule is proportional: use held-out and second-executor checks when
the portability claim and risk justify them; otherwise scope the claim, preserve
the evidence, and revisit after a concrete miss.

## Cross-Project Feedback

- When an improvement claim is meant to travel, name the supported harness,
  executor, task distribution, and budget. Do not call one benchmark win
  portable by default.
- Keep motivating cases separate from held-out cases. For high-risk changes,
  check retained invariants at each transition and use project-owned outcome
  oracles.
- Run a second executor only when cross-executor support matters and a small
  discriminating fixture exists. Otherwise pin and document the verified
  executor boundary.
- Treat plugin portability as packaging portability. Recheck installation,
  path containment, permissions, identities, approvals, and data policy in each
  host.
- Keep consequential security, approval, retention, and organization-policy
  decisions with their human or project owner.

  existing record covered the previously identified continuity concern.

## Answer Key

1. The harness, executor, task distribution, and budget. The executor includes
   model, client, runtime, permissions, and versions; the budget includes time,
   tokens, tool calls, and human review.
2. It may have overfit the motivating cases, regress held-out behavior, consume
   more resources, or interact differently with another model or runtime. The
   supported claim must match the combinations actually evaluated.
3. Compare baseline and candidate on the motivating 429 case, held-out rate
   limits, other failures, idempotency-sensitive operations, and a normal
   success. Measure correctness, forbidden duplicate writes, latency, and token
   cost, with the current executor as the primary comparison.
4. It standardizes the package layout for skills, MCP configuration, metadata,
   and related resources. Runtime semantics, sandboxing, permissions, identity,
   approvals, installation trust, and data policy remain responsibilities of
   each host and organization.
