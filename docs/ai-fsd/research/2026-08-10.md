## Learning Article

### The reviewer and the permission boundary are different controls

A useful mental model is to separate two questions: **what is allowed to run?**
and **who decides when a boundary may be crossed?** The first is the permission
boundary: sandbox mode, writable paths, network policy, credentials, protected
resources, and approval categories. The second is the reviewer: a human or an
automated agent that evaluates a specific request produced by that boundary.

This matters because faster approvals can look like broader authority even when
the underlying permissions have not changed. Confusing the two can produce
opposite mistakes. A team may fear that any automated reviewer has unrestricted
access, or it may trust an automated review as if it granted blanket permission.
The safer statement is narrower: the reviewer can approve only a request the
existing policy exposes, and the execution still runs inside the configured
limits.

Before today, the harness already required least privilege, explicit trust
boundaries, behavioral security evidence, and escalation for security judgment.
It also had a deferred decision covering automated approvals, plugins, runners,
and cross-session authority. Today's official documentation sharpens the mental
model but does not change the harness. No approval failure was reproduced here,
the current task has no interactive approval surface to exercise, and a generic
security rule would need a threat model plus negative tests. Deliberately doing
nothing is the evidence-gated choice.

In another project, imagine a release agent that may read the repository and
call a staging deployment endpoint, but has no production credential. An
automated reviewer could approve a request to reach the allowlisted staging
endpoint after checking the command and destination. That does not let the agent
write outside its workspace or deploy production. A useful evaluation would
show that the staging request succeeds, a request to send a token to an unknown
host is denied, repeated denials stop rather than loop, and any human override is
narrowly tied to one exact action.

The separation is not a guarantee of safety. A reviewer can misread incomplete
context, its policy can be stale, and a reviewer built by the same provider is
not automatically an independent security authority. Limits can also be
misconfigured before review begins. Keep high-impact production, data,
credential, and policy decisions under human or organization-approved control;
log the exact request and decision; and test both permitted and denied cases.
The common misuse is to measure approval speed while ignoring whether the
permission envelope and denial behavior are correct.

## Knowledge Check

1. What two questions should be separated when evaluating an automated approval
   reviewer?
2. Why does changing the reviewer not automatically expand an agent's authority?
3. A staging agent requests network access to an allowlisted test endpoint, then
   requests access to a production secret store. What evidence should an
   automated-approval evaluation collect for these two requests?
4. Why is one successful recorded-workflow replay insufficient evidence for a
   reusable team skill?

## Answer Key

1. What the permission boundary allows to run, and who reviews a specific
   boundary-crossing request.
2. The sandbox, writable roots, network policy, credentials, protected paths,
   and approval categories remain the execution envelope; the reviewer only
   decides requests that the envelope exposes.
3. It should show the staging request is allowed for the expected command and
   destination, the production-secret request is denied, the rationale is
   recorded, repeated denial does not cause a workaround loop, and any override
   is narrow and explicit.
4. One replay covers one example. It does not test changed inputs, hidden
   decisions, exception paths, unsafe counterexamples, sensitive-data exposure,
   or continued success as the target system changes.
