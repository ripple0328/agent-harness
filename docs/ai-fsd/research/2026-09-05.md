## Learning Article

### A harness learns when evidence changes the next decision

A failed check is an observation. A verified explanation of the failure can
become useful project knowledge. A change to the harness is a separate
intervention that must demonstrate it improves future work. Keeping these steps
distinct prevents the agent from treating every recent incident as a universal
rule.

Before this upgrade, the repository asked agents to create feedback events after
a correction or a QA miss. That is useful but depends on someone noticing and
writing down the signal. The proposed improvement is to derive candidate signals
from artifacts already produced during delivery and route only relevant ones
for analysis. Capture does not itself diagnose causes or approve new rules.

For example, a check fails and then passes on a retry. A poor shortcut records
the latest green status and forgets the first run. Another poor shortcut labels
the test flaky and excludes it. A useful record preserves both attempts, the
checked revision, relevant environment differences, and the evidence location.
The reviewer can then distinguish a repaired defect, an environmental problem,
or actual nondeterminism. A missing explanation remains an open question.

If this exposes a recurring harness miss, propose a narrow change. Evaluate the
original failure, a safe case, and unrelated work; then compare baseline and
candidate behavior on tasks not used to write the change. A faster run that
misses a real failure should not qualify. A test of the event parser proves the
parser works; it does not prove an agent reads the event or makes a better
decision.

Another project can use the same pattern with its own check runner and release
system. Start with a few structured signals and links to their existing
artifacts. Keep facts current, remove or supersede stale notes, and preserve
human decisions about product risk. Add infrastructure only when measurement
shows a real need. The failure modes are evidence overload, private-data
retention, stale summaries, biased graders, and improvement claims based solely
on the examples used to author the new rule.

## Knowledge Check

1. How does an observation differ from durable context and a harness rule?
2. A check passes on its third attempt. What evidence should capture preserve
   before anyone calls it flaky?
3. A new instruction passes its author's examples. What additional comparison
   is needed before calling it a general improvement?
4. Why cannot the published productivity study percentages be combined into one
   expected acceleration target for this harness?
5. A popular skill duplicates the existing debugger process. What would justify
   importing it anyway?

## Answer Key

1. An observation records an event; context curates verified facts and decisions;
   a rule changes future behavior and requires separate justification and review.
2. Preserve all attempts, statuses, revision and environment provenance, and
   source evidence. Investigate whether code, inputs, or infrastructure changed.
3. Compare baseline and candidate on safe, unrelated, and held-out tasks, retain
   important invariants, check final outcomes, and account for noise and cost.
4. The populations, tools, interventions, dates, measurements, and validity limits
   differ. Task output is also not equivalent to production quality.
5. A concrete unmet need, compatible permissions and provenance, and a scoped
   comparison showing enough benefit to outweigh duplicate instructions and cost.
