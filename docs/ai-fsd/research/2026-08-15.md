## Learning Article

### The best score is not the path

A useful mental model for an iterative agent loop is a sequence of states, not
one final number:

`state N --repair--> state N+1`

For each transition, ask two questions: did the target problem improve, and did
the important behavior that already worked remain intact? A repair is not a
clean improvement when it fixes the current error while turning a previously
passing invariant into a failure. The transition matters even if an earlier or
later iteration has the best aggregate score.

This matters because cumulative-best reporting is deliberately monotonic. If a
run scores 6, then 8, then 7, its best-so-far chart still says 8. That summary is
useful for search, but it hides the regression from iteration two to iteration
three. The new infrastructure-as-code study examined the raw trajectory instead
of only the best result. Its strict measurement found previously passing
security checks regressed in a smaller but non-zero share of scenarios. It also
found that a broader detector reported many more regressions because resource
restructuring changed how checks were observed. The lesson is therefore
two-sided: retain important invariants, and validate that the sensor actually
measures the same thing before and after the change.

Before today, the harness already required acceptance-criteria traceability,
behavioral evidence, focused tests, risk-aware fault injection, and rollback.
Rule changes also have to retain ordinary findings and stay quiet on safe and
unrelated cases. Those practices reduce this risk. What the harness did not do
today was add a universal instruction to re-run every past test after every
agent step. The strongest paper is specific to infrastructure security, no
equivalent local failure was reproduced, full revalidation can be expensive,
and choosing which security or business invariants are release-critical belongs
to the project. The signal was recorded as a deferred decision rather than
turned into generic ceremony.

In another project, imagine an agent repairing duplicate checkout submissions.
The target test verifies that a retried request creates only one order. On the
second iteration the agent refactors the transaction boundary and the duplicate
test passes, but a previously passing tenant-isolation test now exposes another
customer's order. A final count such as “nine of ten tests pass” does not express
the severity of that transition. A better bounded loop keeps a small,
domain-owned retention set beside the target test: authorization, tenant
isolation, idempotency, and data-loss protection. After each meaningful patch,
record target movement and any pass-to-fail transition. Stop and restore the
last safe state when a critical invariant regresses; then narrow the repair
rather than piling another speculative change on top.

The approach has limits. Running every test after every edit can dominate cost
and slow feedback, so use a risk-weighted retention set during iteration and the
full required suite at the project's normal gate. Flaky tests can look like
regressions, and structural changes can make a check observe a different
resource, so reproduce surprising transitions before blaming the patch. A green
retention set cannot prove that unlisted behavior is safe. Finally, rollback is
not a substitute for understanding: it restores a known state, while root-cause
analysis and a narrower forward fix still need engineering judgment.

## Cross-Project Feedback

- For high-risk iterative repair, each project should name a small retention set
  of already-passing invariants, record pass-to-fail transitions after meaningful
  patches, and stop or restore when a critical invariant regresses. The project
  owns the invariant list, sensor semantics, runtime budget, and full release
  gate.
- Projects choosing between latest and stable agent clients should canary the
  latest channel on representative safe, violation, and ordinary cases; record
  the client channel and version; and keep a tested downgrade path. Do not infer
  one provider's release policy is universal.
- Projects enabling ambient activity history should use explicit opt-in,
  allowlisted sources where practical, consent for communications involving
  other people, inspection and deletion paths, and a policy that treats a
  generated memory as a locator or hypothesis until the primary artifact is
  read.
- Projects changing tool interfaces should compare the same task and verifier
  under the old and new architecture, including correctness, files accessed,
  steps, tokens, latency, and failure behavior. The reported preprint is a reason
  to measure, not proof that one interface is best everywhere.

## Knowledge Check

   repair loop?
2. What two questions should be asked for each meaningful repair transition?
3. An agent fixes a latency regression, but a previously passing authorization
   test now fails. What should the bounded loop do before continuing, and what
   evidence should it preserve?
4. Why did today's infrastructure-repair signal not justify a universal harness

## Answer Key

1. Cumulative-best keeps only the highest observed score, so a later iteration
   can regress a specific invariant while the reported best value stays
   unchanged.
2. Ask whether the target problem improved and whether important behavior that
   already passed remained intact. Also confirm that the before-and-after sensor
   is measuring the same invariant.
3. Stop the forward loop, reproduce the authorization failure to rule out a
   flaky or changed sensor, and restore the last safe state if the critical
   regression is real. Preserve the patch transition, target-test result,
   retained-test pass-to-fail result, environment provenance, and rollback
   outcome before attempting a narrower fix.
4. The paper is strong primary evidence but is specific to infrastructure
   security, was not reproduced locally, and requires project judgment about
   critical invariants, false positives, and runtime budgets. Revisit after a
   local or adopting project observes a real pass-to-fail invariant transition
   or can evaluate a small, domain-owned retention set with a safe rollback and
   acceptable cost.
