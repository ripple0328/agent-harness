## Learning Article

### Change nothing, change everything: why agent runs need provenance

A normal software build is usually explained by source code plus dependencies
and configuration. An agent run has a wider input surface. A useful mental model
is:

`agent outcome = task + repository + harness + model + tools + permissions + runtime`

The repository can stay at the same commit while a provider updates a model, a
client changes tool behavior, or a permission default shifts. The next run can
then plan differently, call different tools, or miss a check even though your
own diff is empty. The practitioner study calls this the "change nothing, change
everything" effect. It matters because teams otherwise blame the prompt or code
for behavior that entered through an unrecorded execution dependency.

Before today, this harness recorded the branch and revision in each research
note. That protected the code baseline, but not the execution baseline. Today's
small experiment adds an `Execution provenance` field for the configured model,
client/tool version, runtimes, and explicit unknowns. Keep sensitive execution
details in the project's private evidence store; publish only the information
needed to understand the supported comparison and its limits.

The experiment deliberately does not convert the new OpenAI and Anthropic
permission fixes into a generic security rule. Those fixes teach an important
approval-integrity lesson, but applying it safely requires threat modeling,
negative permission tests, and project or platform judgment. Provenance helps us
notice and compare drift; it does not grant permission to redesign security.

In another project, imagine a weekly agent reviews authentication changes. It
finds a missing authorization check for six weeks, then suddenly misses the same
seeded defect even though the prompt and test fixture are unchanged. With
provenance, the team can see that the model or client changed between runs,
rerun the old and new configurations against the same defect set, and decide
whether to pin, adjust, or escalate based on observed behavior rather than
guessing.

Provenance has limits. A model name is not a full reproducible build, providers
may change behavior behind a stable label, and recording versions never replaces
acceptance tests or behavioral evidence. Too much metadata also becomes a tax.
Record only inputs that can explain a result or support a comparison, mark
unknowns plainly, and keep outcome-focused tests as the real oracle.

## Knowledge Check

1. Why can two agent runs against the same git revision produce different
   behavior?
2. Which execution inputs are worth recording in addition to the repository
   revision?
3. A scheduled reviewer starts missing a seeded authorization defect after a
   client update. What comparison should the team run before changing its
   review prompt?
4. Why is an execution-provenance field insufficient evidence for automatically
   adding a new security rule?

## Answer Key

1. The model, tools, permissions, client, runtime, or provider behavior can
   change independently of the repository.
2. The configured model and available build identifier, client or agent-tool
   version, relevant runtimes, permissions or execution mode, and explicit
   unknowns that could explain the outcome.
3. Run the old and new client/model configurations against the same repository,
   prompt, seeded defect set, and acceptance criteria, then compare misses,
   false positives, tool behavior, and evidence.
4. Provenance explains what may have changed; it does not reproduce a threat,
   prove a vulnerability, define an acceptable policy, or supply the negative
   tests and human security judgment needed for a durable rule.
