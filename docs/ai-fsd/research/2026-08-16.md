QuoteBench separates five things that are often collapsed into one score: the
model configuration, the generation contract, the execution transport, the
operating point, and the final-state validator. It replays the same stored
command through different paths, so a failure after adding a parser can be
attributed to the transport rather than to a newly generated answer. The study
also shows why matching direct and wrapped scores can mislead: transport damage
and model compensation can be large and opposite, leaving a small net change.

That is relevant to SSH wrappers, `docker exec ... sh -c`, CI `run` blocks,
JSON string embedding, and any adapter that reparses command text. It does not
mean every tool call needs shell-specific ceremony. Correct serializers and
typed argument boundaries may preserve the action without the studied failure,
and the paper explicitly does not estimate deployment prevalence. The generic
harness already requires behavioral evidence, final-state checks, execution
provenance, rollback, and risk-weighted tests. A new universal rule would be
duplicative until a real command path or evaluation comparison exposes the gap.

Vero contributes a different useful signal: a verifier is part of the system,
not unquestionable ground truth. Its benchmark allows an agent to produce a

full-repository specifications do not belong in every project. The live project
page also exposes inconsistent corpus counts across rendered content and page

## Learning Article

### The command is not the action

A useful mental model for an agent command is a pipeline:

`intent -> generation contract -> serialization -> wrapper/parser -> executor -> final state`

The text produced by the model is only one stage. A tool may place that text in
JSON, interpolate it into another shell command, send it through SSH, wrap it in
a container command, or copy it into a CI `run` block. Every transformation is
part of the executed system. If one stage interprets quotes, dollar signs,
backticks, globs, or newlines differently, a command that was correct when
generated can become wrong before it reaches the target shell.

This matters because familiar success signals can hide the boundary. A zero
exit code proves only that a process returned zero; it does not prove the right
bytes, arguments, files, or remote state were produced. A matched benchmark
score can also hide the mechanism. Suppose a model scores 96% on a direct path
and 95% when told that its command will be wrapped. That one-point difference
looks harmless. But the wrapped path might destroy sixty points of fixed-command
success while the model's boundary-aware generation recovers fifty-nine. The
final score describes that matched configuration, yet it says little about
whether the same command is portable to another path.

Before today, the harness already required execution provenance, behavioral
evidence, deterministic checks, rollback, and reporting of not-verified items.
Those controls encourage final-state verification and help localize provider or
runtime drift. What it did not add today was a universal command-transport gate.
QuoteBench studies one-shot Bash and one deliberately added parser, no equivalent
failure was reproduced here, and many typed tools do not reparse shell text at
all. The signal was recorded as deferred rather than promoted into generic
ceremony.

In another project, imagine a release job that generates a migration command
locally and then runs it through `ssh host "..."`. The command includes a JSON
filter, a dollar sign in a secret placeholder, and a filename containing a
space. A useful test holds the generated command fixed and executes it first on
the direct path and then through the real wrapper in an isolated fixture. The
oracle checks the exact received argument vector, file bytes, database row, and
absence of collateral files. If the direct path passes and the wrapped path
fails, the first repair target is the boundary: use a correct serializer,
structured arguments, or a safely transferred temporary script. Asking the
model to try harder may compensate for one wrapper while leaving the transport
bug in place.

The model has limits. QuoteBench does not measure PowerShell, Windows CMD,
authentication, interactive state, network failure, multi-turn repair, or how
often the problem appears in production. A temporary script introduces file
lifecycle and cleanup concerns; a typed tool can still mishandle strings; and a
final-state oracle can itself be incomplete. Replaying untrusted commands also
needs isolation, timeouts, network restrictions, and safe fixtures. Finally,
do not preserve full sensitive commands merely for provenance: record the
contract, transport, version, and a safe digest or fixture reference when the
payload may contain secrets or personal data.

## Cross-Project Feedback

- A project that wraps agent-generated commands through SSH, containers, CI, or
  nested serializers should document the exact contract and transport, replay
  a fixed hazardous payload across both paths, and validate final state rather
  than exit status alone.
- Prefer structured operations or correct serializers when the target API
  supports them. Use a temporary script only with explicit creation, transfer,
  permissions, cleanup, and rollback handling.
- A project evaluating model or effort changes should keep the command path,
  validator, fixture, runtime, and query window fixed. If the path itself is
  under evaluation, cross contract and transport rather than comparing only
  matched configurations.
- Formal verification is appropriate only where the project owns meaningful
  specifications and proof maintenance. Even then, retain a way to challenge an
  inconsistent specification or reference implementation with machine-checked
  evidence.
- No adopting project was changed. No feedback event was created because no
  local or repeated generic harness miss was observed.

## Knowledge Check

1. What stages sit between an agent's intent and the final state, and which of
   them can change the meaning of a generated command?
2. Why can two nearly equal matched execution scores hide a large command-path
   problem?
3. A fixed command works locally but corrupts a JSON value when executed through
   `ssh host "..."`, while the wrapper still exits zero. What comparison and
   oracle should the project use, and where should it try to fix the problem
   first?
4. Why did today's evidence not justify a universal command-transport rule or a
   repository-wide formal-proof requirement?

## Answer Key

1. The pipeline includes the generation contract, serialization, any wrapper or
   parser, the executor, and the final-state validator. Serialization, quoting,
   interpolation, reparsing, and execution can all alter or misinterpret the
   command after generation.
2. The transport can damage a fixed command while a model that knows the
   boundary generates compensating syntax. Those large opposite effects can
   cancel in the final matched score, so the net difference hides portability
   and attribution.
3. Replay the same stored command through the direct and real SSH paths in an
   isolated fixture. Validate the exact received arguments, JSON, files or data
   state, and collateral effects rather than exit status. Fix the transport
   boundary first with correct escaping or serialization, a structured argument
   interface, or a safely managed temporary script.
4. QuoteBench is a narrow one-shot Bash study and no equivalent local miss was
   reproduced; existing rules already require behavioral evidence. Vero needs
   project-owned formal specifications, proof tooling, runtime budget, and
   maintenance judgment, and its benchmark was not run here.
