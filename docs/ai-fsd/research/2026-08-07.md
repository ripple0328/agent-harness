## Learning Article

### A pass can teach the wrong lesson: feedback amplification in evolving agents

The useful mental model is a two-step loop:

`task result -> retained lesson -> future task behavior`

A normal delivery error can damage one change. A learning error has a larger
blast radius because it changes how later work is done. If a test suite says a
bad patch is good, and an agent turns that result into memory, a reusable skill,
or a harness rule, the original blind spot becomes a repeatable procedure. The
new survey calls out exactly this problem: executable feedback is valuable, but
tests, logs, benchmarks, and verifiers can be incomplete or misleading.

This matters for software delivery because agent improvement is increasingly
stored outside the model. Repository instructions, memories, skills, hooks,
workflow topology, and feedback events all shape future behavior. Their source
evidence therefore needs a higher bar than a one-off suggestion. The more durable
the lesson, the more independent the verification should be.

Before today, this harness already required a concrete observed miss, hard
evidence, the smallest reversible change, and verification against the original
failure. Today's research did not add another rule. The survey independently
supports that existing design, but repeating it elsewhere would add instruction
cost without changing behavior. The cross-vendor plugin and runner changes were
also deliberately deferred: they raise real supply-chain and authority questions,
but answering them safely requires a concrete failure, a threat model, and
negative tests rather than a scheduled documentation edit.

Consider a dependency-upgrade agent in another project. It upgrades a database
driver, sees unit tests pass, and proposes the lesson "driver upgrades are safe
when unit tests are green." Do not promote that lesson yet. Quarantine it as a
candidate, run the migration and rollback tests against a disposable database,
exercise the supported runtime matrix, and compare production-facing behavior.
Only then distill the specific reusable procedure: which checks matter, which
versions were covered, and what remains unknown. The result is a skill grounded
in observable delivery evidence rather than a lucky green test.

The limitation is that stronger feedback gates cost time and can become an excuse
never to learn. Multiple checks can also share the same blind spot, so their count
alone does not make them independent. Use risk to set the bar: a low-impact,
reversible documentation experiment can learn cheaply; a security, data, or
release rule needs stronger oracles and human judgment. The goal is controlled
learning, not frozen behavior.

## Answer Key

1. It can be retained and reused, so one false result changes future behavior
   across many tasks instead of harming only the current task.
2. Repository memory, reusable skills and tools, workflow or agent topology,
   harness rules and hooks, and model or policy updates.
3. No. First run the missing migration and rollback tests in a disposable
   environment, cover the supported runtime matrix, compare observable behavior,
   and record limits and rollback before promoting a narrowly scoped skill.
4. The releases prove vendor behavior, not a local harness failure. A durable
   security rule needs a concrete reproduced miss, threat modeling, safe negative
   tests, and human security or architecture judgment.
