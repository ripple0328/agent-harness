## Learning Article

### A finished step is not a finished workflow

A useful mental model for long-running or multi-agent work is a chain:

`work completes -> result is durable -> handoff arrives -> next actor resumes -> outcome is observed`

Each arrow is a separate reliability boundary. A background agent can finish its
code change while the parent never receives the message. A runner can persist an
artifact but exit before the follow-up turn. A resumed session can wake with the
wrong conversation state. Calling the first step “success” would hide a delivery
failure in the workflow around it.

This matters because AI-first delivery increasingly spans scheduled tasks,
background workers, sub-agents, remote sessions, and human approvals. Tests can
prove the patch is correct while orchestration still loses it, duplicates it, or
resumes with stale authority. Reliable delivery therefore needs both work
correctness and continuity evidence.

Before today, the harness already required bounded tool loops, stop conditions,
structured packets, and auditable outcomes. It also had a deferred decision for
runner and cross-session controls. Today's Claude Code release gives concrete
examples of continuity failures in that product, but this run did not add a
generic rule. No equivalent failure was reproduced in the canonical harness,
and changes involving session isolation, cleanup, or permissions need safe
negative tests and appropriate judgment. Active-SWE and GitHub memory were also
recorded without being promoted into broad behavior.

In another project, imagine a nightly dependency agent. A worker updates a
library and passes tests, then a parent is supposed to review the diff and open a
pull request. Give the run one correlation ID and require five observable facts:
the worker's terminal status, a durable diff or commit reference, a handoff tied
to that ID, parent acknowledgement and wakeup, and the final pull-request or
explicit no-PR outcome. On retry, the parent should re-read the durable artifact
and check current repository state instead of trusting message text. If the
worker finished but acknowledgement never arrived, classify the run as a
continuity failure rather than a successful update.

The tradeoff is instrumentation and retry complexity. Exactly-once delivery is
often unrealistic; at-least-once delivery plus idempotent handling is usually a
safer design. Heartbeats can become noise, acknowledgements can lie, and a
durable artifact can still be stale or malicious. Continuity checks do not prove
the code is correct, and behavioral tests do not prove the handoff occurred.
Use the smallest evidence chain justified by the workflow's risk, keep sensitive
conversation state out of generic traces, and test failure boundaries rather
than merely adding status fields.

## Cross-Project Feedback

- Projects using scheduled, background, remote, or multi-agent delivery should
  define a local handoff contract only where a real workflow needs it: correlation
  ID, durable artifact, terminal status, receipt or wakeup evidence, idempotent
  retry, and final observed outcome.
- Validate that contract with one safe injected failure, such as suppressing a
  handoff or replaying it, while confirming ordinary successful work remains
  quiet. Return lost, duplicate, stale-state, or cleanup incidents to the
  canonical harness before proposing a generic rule.
- Projects evaluating review agents can distinguish reactive review from a
  bounded proactive audit. Use historical escaped bugs or seeded faults in a
  disposable scope, hide the issue description, and measure localization plus
  repair with an independent oracle before adopting an Active-SWE-like gate.
- Projects enabling cross-session memory should keep retention, inspection,
  privacy, and deletion rules local and verify remembered claims before turning
  them into skills or instructions.

## Answer Key

1. Work completion, durable result, delivered handoff, resumed next actor, and
   observed terminal outcome.
2. The result can still be lost, duplicated, resumed under stale or wrong state,
   or abandoned before the next actor and final outcome, so task correctness and
   workflow continuity are different properties.
3. Classify it as a continuity failure, not a successful update. Reuse the
   correlation ID, re-read the durable diff or commit, verify current repository
   state, and make acknowledgement and final outcome idempotent.
4. The release proves defects and fixes in one vendor product, not a reproduced
   miss in this harness. Revisit after a concrete local or adopting-project
   handoff, runner, state-isolation, or cleanup failure that can be tested with a
   safe failure injection, rollback, and any required security or architecture
   judgment.
