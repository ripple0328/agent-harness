## Learning Article

### A skill is a treatment, so measure the delta

A useful mental model for evaluating an agent skill is a controlled comparison:

`same task + same environment + different skill setup -> outcome, cost, and trajectory delta`

Treat the skill as the one changed input. Hold the task, repository state, model,
agent runtime, verifier, and relevant data fixed. Compare the skill-guided run
with a no-skill run or a run using another relevant skill. A failure in the
skill-guided run is stronger evidence of harm when the reference run passes. If
both pass but the skill uses much more time or tokens, that is an efficiency
regression candidate rather than an automatic success.

This matters for software delivery because skills are active instructions, not
passive documentation. They influence planning, file placement, dependencies,
commands, validation, and stopping. Relevant-sounding guidance can still fill a
required field incorrectly, omit task-specific behavior, validate against the
wrong environment, or turn a useful checklist into mandatory work for every
task. Reusing that skill then repeats the bias across projects.

Before today, the harness already required rule and instruction changes to be
tested on an intended violation, a safe counterexample, unrelated work, ordinary
finding retention, and actionability. A `SKILL.md` file is an instruction
surface, so those controls already apply. OpenAI's skill-eval guide also frames
an eval as a prompt, captured run and artifacts, focused checks, and a comparable
score, including outcome and efficiency goals. Today's new paper strengthens the
case for paired skill/no-skill evidence, but this run deliberately did not add a
new generic rule. The paper is newly submitted, its results were not reproduced
here, and no real harness skill change has escaped the existing controls.

In another project, imagine a release skill that asks an agent to build, run the
full suite, scan dependencies, generate notes, and prepare deployment evidence.
Evaluate it on three cases: a risky database migration where the full procedure
should help, a documentation-only change where the skill should stay quiet, and
a routine dependency patch where a smaller verification slice may be enough.
Run each case with and without the skill under the same model and repository
snapshot. Compare acceptance-test results, files touched, commands, elapsed time,
and token use. Keep the skill only if it improves the risky case without breaking
the safe case or imposing unjustified procedure on ordinary work. If it doubles
cost on the migration but catches a rollback defect, that may be worthwhile; if
it doubles cost on documentation and changes unrelated files, narrow its trigger
or procedure.

The method has limits. Agent runs are nondeterministic, so one pair can confuse
normal variance with a skill effect; repeated or seeded cases are stronger but
cost more. A no-skill run is a pseudo-oracle, not truth, and a cheaper run may be
less safe. Token and time thresholds are policy choices, not universal quality
measures. Differential evaluation also does not replace security review: a skill
can preserve the final result while taking an unsafe or attacker-controlled
trajectory. Use paired evidence to localize effects, then apply the project's
normal correctness, security, privacy, and release judgment.

  and without the skill, or against a matched skill, while holding the repository,

## Knowledge Check

1. In a differential skill evaluation, which inputs should stay fixed and which
   input should change?
2. Why does one successful skill-guided run not prove that the skill helped?
3. A release task passes both with and without a skill, but the skill-guided run
   takes twice as long and uses more tokens. How should that result be classified,
   and what project context determines whether it is acceptable?
4. Why did the new skill-regression paper not justify a generic harness change
   today, and what future evidence would reopen the decision?

## Answer Key

1. Keep the task, repository and data state, model, agent runtime, verifier, and
   other relevant conditions fixed; change only the skill setup, such as skill
   versus no skill or one matched skill versus another.
2. The base agent may already solve the task, the skill may add no value, or it
   may make the trajectory slower or riskier. A comparable reference run is
   needed to estimate the skill's marginal effect.
3. Treat it as an efficiency-regression candidate. Decide whether it is
   acceptable from the task's risk, the defects or evidence the extra work adds,
   local cost and latency budgets, and whether a narrower trigger or procedure
   preserves the benefit.
4. The paper is a new preprint whose results were not reproduced locally, and the
   harness's existing rule/instruction controls already cover skill instructions.
   Revisit after a real local or adopting-project skill change shows a functional
   or material efficiency regression that escapes those controls and can be
   tested with a bounded comparison and rollback.
