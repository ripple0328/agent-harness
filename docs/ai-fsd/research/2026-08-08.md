## Learning Article

### A rule is a classifier: test when it should fire and when it should stay quiet

The useful mental model is simple: every review rule divides changes into two
groups. Some changes should trigger the rule; safe or unrelated changes should
not. Testing only the first group proves that the rule can fire. It says nothing
about whether the rule fires everywhere, distracts reviewers, or hides ordinary
bugs behind a wall of special-purpose findings.

That matters in AI-first software delivery because written guidance is cheap to
add and expensive to carry. Agents can apply a broad instruction repeatedly
across thousands of diffs. A noisy rule consumes scarce reviewer attention,
teaches people to ignore automated findings, and may compete with the general
review that would have caught a different defect. Verification therefore needs
both sensitivity and restraint.

Before today, the harness told maintainers to verify a change against the
original evidence and avoid overfitting. That was directionally right but
underspecified: a rule could catch the motivating example and still be declared
successful without any clean control. Today's bounded experiment makes the
control set explicit. When feasible, a new rule or instruction is exercised on
the intended violation, a safe counterexample, and an unrelated change. The
maintainer also checks that ordinary findings remain visible and that the result
explains a useful next action. No adopting project was changed.

Imagine another project repeatedly breaks a mobile API by renaming a response
field that older clients still consume. Add a scoped compatibility rule, then
test three diffs: one that renames the field without a migration, one that adds a
new optional field while preserving the old wire name, and one that changes an
unrelated documentation page. The first should produce a focused finding; the
other two should stay quiet. Finally, include an ordinary authorization bug in a
representative review to confirm the compatibility guidance did not crowd out
general review. The finding should name the invariant and a safe path, such as
preserving the field or versioning the contract.

The limitation is that three examples are not a full eval suite. Poorly chosen
counterexamples can make a bad rule look restrained, and model or tool updates
can change behavior later. Control cases also add cost, so use them where a rule
will be durable or consequential; keep formatting and other deterministic checks
in CI. If a rule continues to create noise, narrow its scope, improve the safe
path, or remove it instead of adding more prose.

3. A repository rule flags every API-schema edit, including additive optional

4. Why should an ordinary bug remain in the verification set when testing a new
   specialized review rule?

## Answer Key

1. The trigger proves sensitivity, not restraint. A safe counterexample reveals
   whether the rule creates false positives on acceptable work.
2. The intended violation, a safe counterexample, and an unrelated change.
3. The rule is too broad and noisy. Narrow it to the actual compatibility
   invariant, state the safe path, and rerun all controls before keeping it.
4. It checks retention: the specialized guidance must not crowd out or suppress
   the review system's ordinary defect-finding ability.
