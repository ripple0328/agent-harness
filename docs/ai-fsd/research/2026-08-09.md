## Learning Article

### A failed sensor means unknown, not zero

A useful mental model for delivery evidence is `system state -> sensor ->
observation`. Tests, logs, source connectors, health checks, and release feeds are
all sensors. When a sensor works, its observation can support a scoped claim.
When it fails, the underlying system state does not become empty or healthy; it
becomes unknown through that path.

This matters in AI-first software delivery because agents are very good at
turning a returned list into a confident summary. A query that returns no rows
can mean there were no matching events, but a quota error, timeout, permission
gap, or partial index means something different: the evidence surface was not
available. Treating both as zero creates false confidence and can let missing
tests, silent telemetry gaps, or inaccessible review queues masquerade as good
news.

Before today, this harness already required source failures, authentication
gaps, timeouts, and not-verified items to be explicit. It also treated discovery
sources as leads rather than proof. An unavailable source therefore leaves a
coverage gap; a different source may support a narrower claim without replacing
the missing evidence. No new rule was applied because the workflow already
describes this distinction.

In another project, imagine a deployment dashboard shows the primary region as
healthy while its credentials for the secondary region have expired. The right
packet says "primary region passed its checks; secondary region not verified due
to authentication failure." It must not say "global deployment healthy." A
useful next action is to repair the credential or run a separate read-only
synthetic check against the secondary endpoint, while keeping the verified
primary result intact.

The limitation is that `unknown` is not the same as `unsafe`, and declaring
everything blocked whenever one sensor fails creates paralysis. Scope the claim,
use independent fallbacks, and make a risk-weighted decision. Retry with sensible
backoff, but do not spend repeated calls at a known quota boundary. The common
misuse is either extreme: converting missing evidence into success, or treating
every coverage gap as proof of failure.

## Cross-Project Feedback

- Preserve a three-state result for meaningful evidence surfaces: `pass`,
  `fail`, or `not verified`, with the affected scope and failure reason.
- Use a fallback only for the claim it can actually support. A related feed
  cannot prove the contents of an unavailable source; a process health check
  cannot prove a user-visible journey.
- Do not copy vendor-specific trajectory or security fields into the generic
  harness. A project that cannot explain a behavior change should first return a
  sanitized comparison case, then decide locally what extra evidence is safe.

## Knowledge Check

1. Why does a failed connector not support the claim that there were zero new
   matching records?
2. What are the three useful result states for a delivery evidence surface?
3. A release pipeline's build and unit tests pass, but its production smoke test
   times out before reaching the service. What may the team claim, and what must
   remain not verified?
4. When is a fallback source sufficient to close a coverage gap?

## Answer Key

1. The failure removes observation coverage; it says nothing conclusive about
   the underlying records.
2. `pass`, `fail`, and `not verified`, each scoped to the surface actually
   checked.
3. The build and unit-test results may be reported as passed. Production
   reachability and user-visible behavior remain not verified until an
   independent production check succeeds.
4. Only when the fallback observes the same relevant state with enough authority
   and scope. A related but narrower source can provide partial evidence, not
   silently replace the missing surface.
